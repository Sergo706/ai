Multi-stage workflows can run for minutes across dozens of LLM and web requests. If a worker restarts or a container is evicted halfway through round 3, re-running from scratch wastes both latency and API spend. `AgenticWorkflowLoop` exposes first-class checkpointing hooks that integrate seamlessly with the [Run System](/runs) or any custom key-value/SQL store.

## How checkpointing works

At every durable boundary (after `seeds`, after local batches, after each external round, and after `critic`), the loop invokes `onCheckpoint(snapshot)` with a JSON-serializable `WorkflowCheckpoint`:

```ts [WorkflowCheckpoint Shape]
interface WorkflowCheckpoint {
  completedStages: WorkflowStage[]; // Stages already finished — skipped on resume
  localSearches: number; // Local budget already spent
  externalRounds: number; // External budget already spent
  state: unknown; // WorkflowStateSnapshot (Maps/Sets flattened to arrays)
}
```

When you later pass that object back through `resumeFrom`, `AgenticWorkflowLoop` restores `WorkflowState` (including `evidenceSet`, `localItems`, `externalArtifacts`, `issuedIntents`, `exhaustedIntents`, `seenLocalIds`, `attemptedTargets`, and spent round counts) and skips every stage listed in `completedStages`.

::warning
**Checkpoints are for crash recovery, not human-in-the-loop (HITL) pauses.** `AgenticWorkflowLoop` does not support suspending a live run to wait for human approval or interactive user input and then continuing in place. To implement an approval gate, finish or abort the first run cleanly, persist its result or checkpoint in your application, collect the user's decision, and start a new run once approved.
::

## Wire `onCheckpoint` and `resumeFrom`

The example below pairs `AgenticWorkflowLoop` with `runWorkflow()`, `checkpoint()`, `parseCheckpoint()`, and `saveCheckpoint()` from the [Run System](/runs/checkpoints-and-workflows):

```ts [src/durable-workflow.ts]
import {
  AgenticWorkflowLoop,
  checkpoint,
  getConfiguration,
  parseCheckpoint,
  runWorkflow,
  type WorkflowCheckpoint,
} from "@riavzon/ai";

const CHECKPOINT_SPEC = {
  version: 1,
  phases: ["seeds", "local", "external", "critic", "final"] as const,
};

export async function runDurableResearch(params: {
  runId?: string;
  resumeRunId?: string;
  userId: string;
  query: string;
  conversationId?: number;
}) {
  const log = getConfiguration().logger;

  return runWorkflow(
    {
      runId: params.runId,
      resumeRunId: params.resumeRunId,
      kind: "workflow",
      name: "research",
      query: params.query,
      userId: params.userId,
      conversationId: params.conversationId,
      input: { query: params.query },
    },
    async (ctx) => {
      // Load prior loop checkpoint if adopting an interrupted run
      const rawCheckpoint = await ctx.loadCheckpoint();
      const parsed = parseCheckpoint<
        WorkflowCheckpoint,
        (typeof CHECKPOINT_SPEC.phases)[number]
      >(rawCheckpoint, CHECKPOINT_SPEC);

      const loop = new AgenticWorkflowLoop({
        ...buildAdapters(params.query),
        name: "research",
        query: params.query,
        signal: ctx.leaseSignal,
        resumeFrom: parsed?.state,
        onProgress: ctx.emitProgress,
        onCheckpoint: (snapshot) => {
          const latestStage =
            snapshot.completedStages[snapshot.completedStages.length - 1] ??
            "seeds";
          ctx.saveCheckpoint(
            checkpoint({
              phase: latestStage,
              state: snapshot,
              roundsDone: snapshot.externalRounds,
            }),
          );
        },
      });

      const result = await loop.run();
      return {
        data: result.report,
        stopReason: result.stopReason,
        source: result.source,
        isSufficient: result.isSufficient,
        missingIntents: result.missingIntents,
      };
    },
    log,
  );
}
```

## Work with `WorkflowState` directly

If you inspect or restore state outside the loop (for example in tests or a custom multi-step orchestrator), `WorkflowState` exposes `toCheckpoint()` and `restore()` directly:

```ts [src/state-snapshot.ts]
import { WorkflowState } from "@riavzon/ai";

const state = new WorkflowState<string, { url: string }>(
  "initial query",
  budgets,
);
state.appendEvidence("Verified pricing paragraph");

// Serialize to plain JSON (Maps & Sets become entry/value arrays)
const snapshot = state.toCheckpoint();
const json = JSON.stringify(snapshot);

// Hydrate into a fresh state instance with current budgets
const resumed = new WorkflowState<string, { url: string }>(
  "initial query",
  budgets,
);
resumed.restore(JSON.parse(json));
```

## Cancellation & `WorkflowAbortedError`

Pass an `AbortSignal` into `config.signal`. The loop checks `signal.aborted` between stages and forwards `signal` into every adapter via `context.signal`.

Inside adapters, call `context.signal?.throwIfAborted()` (or throw `new WorkflowAbortedError(workflowName)` when aborted) instead of catching aborts and pushing them into `state.errors`. When the signal fires, `loop.run()` catches the abort, marks the workflow aborted, and **resolves** with `stopReason: "aborted"` (rather than throwing) while returning all evidence and artifacts gathered so far:

```ts [src/handle-abort.ts]
import { AgenticWorkflowLoop, WorkflowAbortedError } from "@riavzon/ai";

const result = await new AgenticWorkflowLoop(config).run();

if (result.stopReason === "aborted") {
  console.log(
    "Workflow cancelled cleanly; collected evidence items:",
    result.externalArtifacts.length,
  );
} else {
  console.log(
    "Completed:",
    result.stopReason,
    "sufficient:",
    result.isSufficient,
  );
}

// Inside a custom adapter catch block — never swallow an abort into state.errors:
async function safeFetch(url: string, signal?: AbortSignal) {
  try {
    return await fetch(url, { signal });
  } catch (err) {
    if (signal?.aborted) {
      throw new WorkflowAbortedError("research"); // Caught by loop.run() -> stopReason: "aborted"
    }
    throw err;
  }
}
```

## Checkpoint invariants and common traps

- **Save the full checkpoint unmodified**: `localSearches` and `externalRounds` appear both at the top level of `WorkflowCheckpoint` (for resuming local and external loops at the right round) and inside `state` (for result reporting). Save and pass back the entire snapshot as-is.
- **Budgets stay fresh across deploys**: `WorkflowBudgets` are omitted from checkpoints on purpose, so tightening or raising budgets takes effect immediately when adopting older runs.
- **Avoid these six adapter traps**:
  1. **Returning `true` from `executeBatch` without adding evidence**: Triggers an unnecessary evaluator call over unchanged evidence and skews `result.source`.
  2. **Assuming `result.report` is always defined**: Final synthesis is skipped whenever `context`, `localItems`, and `externalArtifacts` are all empty — always handle an `undefined` report.
  3. **Logging aborts as recoverable errors**: Pushing an aborted fetch into `state.errors` delays exit. Rethrow when `ctx.signal?.aborted` (via `ctx.signal.throwIfAborted()` or `new WorkflowAbortedError(name)`) so the loop unwinds immediately.
  4. **Mutating or truncating `completedStages`**: Removing completed stages forces resumed runs to replay already-finished work.
  5. **Counting passive snippets as executed sources**: Use `extractPassiveEvidence` on `ExternalDiscoveryAdapter` for inline search snippets rather than treating them as executed targets; passive evidence enriches `evidenceSet` without hiding rounds where every candidate target was already attempted (`maxSkippedExternalRounds`).
  6. **Expecting `isSufficient: true` on empty evidence**: The loop refuses to treat an empty `evidenceSet` as sufficient, preventing early exit before any evidence is gathered.

::note
Because `onCheckpoint` fires after every completed stage and external round, an aborted or crashed run retains all evidence gathered before cancellation. If you later retry or adopt the run, `resumeFrom` picks up immediately without redoing completed stages. For the full production setup (`boot` → `registerRunResumer()` → runner → HTTP routes), see [Registering a Workflow Runner](/runs/registering-a-workflow-runner).
::
