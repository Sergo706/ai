Without durable runs, a chat turn dies the moment an HTTP connection drops or a container restarts. Enabling `runs` on `createAgent()` wraps every turn in the `@riavzon/ai` run lifecycle: a row is written to `runs` before any provider call begins, a lease prevents duplicate execution across replicas, every emitted event is recorded in the event store, and clients can reattach seamlessly after a disconnect.

## Enable `runs` on `createAgent()`

`runs` requires `conversation: { persist: true }`. If you omit `conversation` or set `persist: false`, `createAgent()` throws at construction.

```ts [src/durable-agent.ts]
import { createAgent } from "@riavzon/ai";

export const durableAgent = await createAgent({
  model: {
    model: "gpt-4o-mini",
    tools: { maxRounds: 8 },
  },
  systemInstructions: "You are a thorough research assistant.",
  tools: {
    common: ["search_db", "get_document", "calculator"],
  },
  conversation: {
    persist: true,
  },
  runs: {
    kind: "chat",
    name: "support-assistant",
    registry: true,
  },
});
```

::field-group
:::field{name="kind" type="RunKind" default="chat"}
Value stored in `runs.kind` (`"chat" | "workflow"` or any custom `RunKind` string).
:::

:::field{name="name" type="string"}
Optional discriminator written to `runs.input.name`. Use this when multiple agents share the same `kind` and recovery needs to distinguish them.
:::

:::field{name="registry" type="boolean" default="true"}
Reserved option on `RunOptions`. Currently, enabling `runs` on `createAgent()` always registers an in-process `RunHandle` (`getRun`, `streamFromRun`) for every turn so same-process SSE reattach and stop-button cancellation work immediately without waiting on Redis.
:::
::

## Stream and reattach from HTTP routes

When `runs` is enabled, `agent.chat()` starts the turn eagerly in the background (unlike non-run turns, which start lazily on first read).

::note
The `init` frame emitted directly by `agent.chat()` carries `{ type: "init", conversationId }` without `runId`. Mint `runId` in your route handler (`const runId = crypto.randomUUID()`), pass it into `agent.chat({ runId, ... })`, and return it to your frontend via a response header (such as `X-Run-Id`), or stream through `streamFromRun({ run, conversationId, runId, log })` — whose `init` frame carries both `conversationId` and `runId`. `ChatTurnResult.runId` also resolves to the exact `runId`.
::

### Start endpoint (`POST /api/chat`)

```ts [src/routes/chat.ts]
import { framesToStream, setSseHeaders } from "@riavzon/ai";
import { durableAgent } from "../durable-agent";

export async function POST(req: Request): Promise<Response> {
  const { message, userId, conversationId } = (await req.json()) as {
    message: string;
    userId: string;
    conversationId?: number;
  };

  const runId = crypto.randomUUID();
  const chat = await durableAgent.chat({
    message,
    userId,
    conversationId,
    runId,
  });

  // Omit onCancel so a dropped browser tab does NOT abort the durable turn
  return new Response(framesToStream(chat.frames), {
    headers: {
      ...setSseHeaders(),
      "X-Run-Id": runId,
    },
  });
}
```

### Reattach endpoint (`GET /api/runs/:id/stream`)

If the client disconnects (page refresh, mobile network switch, or load balancer timeout), reconnect with the `Last-Event-ID` header or a `?since=` query parameter. Check the local registry first (`streamFromRun()`), then fall back to Redis Streams (`streamFromStore()`) so requests routed to a different replica replay and tail live events seamlessly.

```ts [src/routes/runs-stream.ts]
import {
  FIRST_ID,
  getConfiguration,
  getRun,
  getRunById,
  setSseHeaders,
  streamFromRun,
  streamFromStore,
} from "@riavzon/ai";

export async function GET(req: Request, runId: string): Promise<Response> {
  const url = new URL(req.url);
  const since =
    req.headers.get("last-event-id") ??
    url.searchParams.get("since") ??
    FIRST_ID;
  const log = getConfiguration().logger;

  // Fast path: run is hosted in this process
  const localRun = getRun(runId);
  if (localRun) {
    return new Response(
      streamFromRun({
        run: localRun,
        since,
        conversationId: localRun.conversationId,
        runId: localRun.id,
        log,
      }),
      { headers: setSseHeaders() },
    );
  }

  // Cross-replica path: replay and tail from Redis Streams
  const row = await getRunById(runId);
  if (!row) {
    return new Response("Run not found", { status: 404 });
  }

  return new Response(
    streamFromStore({
      runId,
      since,
      conversationId: row.conversation_id ?? undefined,
      log,
      isRunAlive: async () => {
        const latest = await getRunById(runId);
        return latest?.status === "running";
      },
    }),
    { headers: setSseHeaders() },
  );
}
```

### Stop button endpoint (`POST /api/runs/:id/stop`)

Abort a run cleanly whether the stop request lands on the owning replica or another replica:

```ts [src/routes/runs-stop.ts]
import { getRun, requestAbort } from "@riavzon/ai";

export async function POST(runId: string): Promise<Response> {
  // 1. Mark aborted in the database so the owning replica's heartbeat stops it
  await requestAbort(runId);

  // 2. If hosted locally, abort the in-flight AbortController immediately
  getRun(runId)?.controller.abort();

  return Response.json({ ok: true, runId });
}
```

### Interaction with semantic cache and validated JSON

- **Run-backed semantic cache hits**: When `semanticCache` is also enabled, a cache hit still records a finished `runs` row, publishes `chunk` and `done` to the event store, and returns both `runId` and `cached: true`. Reattach endpoints (`getRunById()`, `streamFromRun()`, `streamFromStore()`) work identically for cached and live turns.
- **Validated JSON failures**: When a run-backed turn uses `json: { validate: true, schema }`, validation or provider failures mark the `runs` row `aborted` or `failed` and **rethrow** to the caller.

::tip
Call `startRuns()` once after `configuration()` at server boot so abandoned runs left behind by a crashed process are marked `"interrupted"` and picked up by registered resumers. See [The Run System](/runs) for full lifecycle details.
::
