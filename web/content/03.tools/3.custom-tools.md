A `ToolSpec<TMeta>` describes a tool once — its OpenAI JSON Schema definition, per-request factory, caching policy, call limit, concurrency width, and SSE streaming policy. You can pass `ToolSpec[]` to `createAgent({ tools: { specs } })` or compile them yourself with `buildToolRegistry()`.

## Anatomy of a `ToolSpec` and typed handler factory

Keep tool logic in a standalone **factory function returning a `ToolHandler`** (`export function myTool(deps): ToolHandler`) rather than inlining business logic inside `ToolSpec.make`. Every built-in tool in `@riavzon/ai` (`calculator`, `searchDb`, `getDocument`, `extractor`, `pdfCreator`) follows this pattern because it decouples runtime dependencies (`orgId`, tokens, DB clients) from `ToolSpec` wiring and makes handlers straightforward to unit-test directly.

```ts [src/tools/crmLookup.ts]
import { z } from "zod";
import {
  getConfiguration,
  jsonToMarkdown,
  toolError,
  type ToolHandler,
  type ToolSpec,
} from "@riavzon/ai";

export interface AppMeta {
  orgId: string;
  crmToken: string;
}

export interface CustomerLookupDeps {
  orgId: string;
  crmToken: string;
}

// Use z.strictObject so unknown keys invented by the model fail validation
// with a correctable VALIDATION_ERROR instead of being silently stripped.
const crmArgsSchema = z.strictObject({
  email: z.string().trim().toLowerCase().email(),
  includeTickets: z.boolean().default(false),
});

export function lookupCustomer(deps: CustomerLookupDeps): ToolHandler {
  const log = getConfiguration().logger;

  return async (rawArgs, exec) => {
    log.debug({ rawArgs }, "agent ran tool lookup_customer");

    const parsed = crmArgsSchema.safeParse(rawArgs);
    if (!parsed.success) {
      return toolError("VALIDATION_ERROR", JSON.stringify(parsed.error.issues));
    }

    const res = await fetch(
      `https://crm.internal/orgs/${deps.orgId}/customers?email=${encodeURIComponent(parsed.data.email)}&tickets=${String(parsed.data.includeTickets)}`,
      {
        headers: { Authorization: `Bearer ${deps.crmToken}` },
        signal: exec.signal,
      },
    );

    if (res.status === 404) {
      return toolError(
        "NOT_FOUND",
        `No customer found for ${parsed.data.email}`,
      );
    }
    if (!res.ok) {
      return toolError("CRM_ERROR", `CRM responded with HTTP ${res.status}`);
    }

    return await res.json();
  };
}

export const lookupCustomerSpec: ToolSpec<AppMeta> = {
  name: "lookup_customer",
  definitions: {
    type: "function",
    function: {
      name: "lookup_customer",
      description:
        "Look up a customer profile and recent support tickets by email.",
      // Generates JSON Schema with additionalProperties: false from z.strictObject
      parameters: z.toJSONSchema(crmArgsSchema, { io: "input" }),
    },
  },
  cache: {
    ttl: 300,
    scoped: true,
    // Parse with the same Zod schema so defaulted fields hash identically
    // whether the model omitted `includeTickets` or explicitly passed `false`.
    normalizeArgs: (args) => {
      const parsed = crmArgsSchema.safeParse(args);
      return parsed.success ? parsed.data : args;
    },
  },
  maxCalls: 4,
  concurrency: 2,
  stream: {
    emitArgs: true,
    emitResult: "none",
    serializeForModel: (result) => jsonToMarkdown(result, { maxDepth: 4 }),
  },
  make: (ctx) =>
    lookupCustomer({
      orgId: ctx.meta?.orgId ?? "",
      crmToken: ctx.meta?.crmToken ?? "",
    }),
};
```

### Four handler conventions

1. **Use factories over inline closures**: Write `export function myTool(deps: MyDeps): ToolHandler` and wire `make: (ctx) => myTool(...)`. Passing per-request state (user ID, tenant ID, tokens) into a factory keeps handlers reusable outside `ToolSpec` and straightforward to unit-test.
2. **Log raw arguments first**: Call `log.debug({ rawArgs }, ...)` before validation so invalid model arguments still appear in logs.
3. **Return `toolError(code, message)` instead of throwing**: Return `toolError(...)` for expected failures. `executeToolLoop()` catches uncaught exceptions and replaces them with a generic `TOOL_EXECUTION_FAILED` error so stack traces and internal details never reach the model or end user.
4. **Return non-null JSON-serializable values**: Returning `undefined` triggers `INVALID_TOOL_RESULT`, and values that cannot be serialized to JSON (such as circular objects or `BigInt`) trigger `TOOL_EXECUTION_FAILED`.

### Strict Zod schemas vs. raw JSON Schema

There are two ways to supply `definitions.function.parameters`:

- **Zod `z.strictObject(...)` + `z.toJSONSchema(schema, { io: "input" })` _(recommended)_**: Single source of truth for both the model-facing JSON Schema (including `additionalProperties: false`) and runtime validation inside the handler. If the model invents an extra argument, `safeParse` fails with a `VALIDATION_ERROR` explaining the exact issue so the model can self-correct on the next round.
- **Hand-written raw JSON Schema**: Passed verbatim to the provider, **not** validated at runtime by `@riavzon/ai`. Always validate `args` inside your handler before querying databases or external APIs.

## `ToolSpec` properties

::field-group
:::field{name="name" type="string" required}
Unique tool name matching `definitions.function.name`. Used as the cache key prefix, concurrency bucket key, and `toolsUsed` identifier.
:::

:::field{name="definitions" type="ChatCompletionTool" required}
Standard OpenAI tool definition passed verbatim to `chat.completions.create`. Use Zod 4's `z.toJSONSchema(schema, { io: "input" })` or a plain JSON Schema object.
:::

:::field{name="make" type="(ctx: ToolFactoryContext<TMeta>) => ToolHandler" required}
Factory invoked once per request with `{ userId, conversationId, meta }`. Return a handler `(args, execContext) => unknown`.
:::

:::field{name="cache" type="{ ttl: number; scoped?: boolean; normalizeArgs?: (a) => Record<string, unknown> }"}
Caches non-error results for `ttl` seconds. When `scoped: true`, keys include `ctx.userId`; otherwise the scope is `"global"`. Use `normalizeArgs` to canonicalize casing or strip volatile fields.
:::

:::field{name="maxCalls" type="number"}
Caps invocations of this specific tool per request. Exceeding the cap returns `TOOL_LIMIT_REACHED` instead of running the handler. Also populates `callTotal` in `tool_start`/`tool_end` events.
:::

:::field{name="concurrency" type="number"}
Limits how many parallel calls to this tool execute at once when the model emits multiple tool calls in the same round.
:::

:::field{name="stream" type="ToolStreamPolicy"}
Controls SSE visibility (`emitArgs`, `emitResult: "full" | "preview" | "none"`) and optional model formatting (`serializeForModel`).
:::
::

## `ToolExecutionContext` inside your handler

Every handler receives `(args, context)` where `context` provides live turn metadata:

- **`context.toolCallId`**: provider ID of this tool call.
- **`context.signal`**: `AbortSignal` for the active turn — forward it to `fetch()`, database queries, or child work so clicking Stop actually cancels long-running I/O.
- **`context.callIndex`** / **`context.callTotal`**: 1-based ordinal and planned total for this tool in the request.
- **`context.emit`**: optional `AgentEventEmitter` for emitting live progress events from inside a long-running tool.

## Return structured errors with `toolError()`

Never throw raw exceptions for expected domain failures (missing records, validation errors, rate limits). Return `toolError(code, message)` instead:

```ts [src/tools/error-example.ts]
import { toolError, type ToolHandler } from "@riavzon/ai";

export const lookupOrder: ToolHandler = async (args) => {
  const orderId = String(args.orderId ?? "");
  // Produces: '{"error":{"code":"NOT_FOUND","message":"Order ORD-99 does not exist"}}'
  return toolError("NOT_FOUND", `Order ${orderId} does not exist`);
};
```

The tool loop recognizes `{"error":...}` strings automatically:

1. Sets `ok: false` on the emitted `tool_end` SSE event.
2. Skips writing the result into `withToolCache()` so transient failures are never cached.
3. Passes the error envelope cleanly back to the model as a `tool` message so the model can recover or ask the user to clarify.

## Control SSE disclosure and model formatting (`ToolStreamPolicy`)

`ToolStreamPolicy` decouples what the **model** sees from what the **browser SSE stream** sees:

- **`emitArgs`** _(default `true`)_: set `false` to omit sensitive arguments from `tool_start` SSE frames.
- **`emitResult`** _(default `"preview"`)_:
  - `"full"`: sends the entire serialized tool output in `tool_end.preview`.
  - `"preview"`: truncates `tool_end.preview` at 300 characters.
  - `"none"`: sends `""` in `tool_end.preview` (keeping `tool_start`/`tool_end` UI spinners without leaking large or internal payloads to the client).
- **`serializeForModel`**: transforms non-string handler return values before sending them to the LLM (for example `jsonToMarkdown(result)` to save tokens). Strings returned by handlers bypass `serializeForModel` so `toolError()` envelopes stay intact.

::note
`onToolResult` (used to build persisted `messages.trace`) always receives the full model-facing result rather than the redacted SSE preview, so future conversation turns can replay real tool results.
::

## Low-level registry and wrappers for custom AI clients

If you build your own loop or manage tools outside `createAgent()`, you can use `buildToolRegistry()` or individual wrappers (`withToolCache()`, `limitTool()`, `trackTool()`) directly:

```ts [src/custom-registry.ts]
import {
  buildToolRegistry,
  limitTool,
  trackTool,
  withToolCache,
  type ToolHandler,
} from "@riavzon/ai";

// Option 1: Build a complete registry from ToolSpec[]
const registry = buildToolRegistry(
  { userId: "user_42", conversationId: 12, meta: { orgId: "acme" } },
  [lookupCustomerSpec],
);

console.log(Object.values(registry.definitions)); // ChatCompletionTool[]
console.log(registry.handlers); // Record<string, ToolHandler>
console.log(registry.toolConcurrency); // Record<string, number>
console.log(registry.toolStreaming); // Record<string, ToolStreamPolicy>
console.log(registry.usedTools); // ReadonlySet<string> (filled as tools run)

// Option 2: Compose individual wrappers manually around any ToolHandler
const counts = new Map<string, number>();
const used = new Set<string>();

const rawWeather: ToolHandler = async ({ city }) => ({
  city: String(city),
  tempC: 21,
});

const wrappedWeather = trackTool(
  "get_weather",
  withToolCache(
    "get_weather",
    limitTool("get_weather", 3, rawWeather, counts),
    600,
    "user_42",
  ),
  used,
);
```

## Wrapper order, caching traps & concurrency boundaries

### Why wrapper order is load-bearing

`buildToolRegistry()` always wraps handlers in this exact outer-to-inner order:

```text [Wrapper Composition Order]
trackTool (outermost) ─► withToolCache (middle) ─► limitTool (inner) ─► handler (innermost)
```

Changing this order when composing wrappers manually breaks three invariants:

- **Moving `trackTool` inside `withToolCache`**: Cache hits never record the tool name in `usedTools` — breaking `ChatTurnResult.toolsUsed` and `semanticCache.poisonTools`.
- **Moving `limitTool` outside `withToolCache`**: Identical cache hits consume the per-request `maxCalls` budget and fail once the cap is reached even though no upstream work occurs.
- **Keep `limitTool` inside `withToolCache`**: Only genuine cache misses hit the underlying handler and decrement the call budget.

### Caching traps (`normalizeArgs` and error detection)

- **Defaulted-field cache misses**: `withToolCache()` sorts object keys before hashing, but it runs **before** your handler's Zod validation. If the model omits an optional defaulted field on one call and passes the default value explicitly on the next, the cache keys differ unless `normalizeArgs` parses the arguments through the same schema first.
- **What `withToolCache()` refuses to cache**:
  - Falsy values (`null`, `undefined`, `""`, `false`, `0`).
  - `toolError()` payloads (JSON strings with a top-level `error` object).
  - Any returned object with a truthy `error` property or `ok: false`.
  - Returning a custom failure shape like `{ results: [], failed: true }` without `error` or `ok: false` caches it as a success.
- **Graceful degradation**: Cache read and write errors log a warning and fall through, so a cache outage never fails a tool call or chat turn.

### Call-level vs. item-level `concurrency`

`ToolSpec.concurrency` caps how many **parallel tool calls** to the same tool name execute simultaneously when the model emits multiple calls in one round. It does **not** cap items inside a single batch argument — one call like `extractor({ urls: [u1, ..., u10] })` occupies 1 concurrency slot. Bound per-item fan-out inside your handler (for example with `chunkProcess`).

## Wire error codes & troubleshooting

### Built-in `toolError()` codes

| Code                    | Emitted by         | Meaning                                                                                 |
| ----------------------- | ------------------ | --------------------------------------------------------------------------------------- |
| `UNSUPPORTED_TOOL_TYPE` | `executeToolLoop`  | Provider emitted a non-`function` tool call.                                            |
| `UNKNOWN_TOOL`          | `executeToolLoop`  | Model called a tool name not in `availableTools`.                                       |
| `INVALID_ARGUMENTS`     | `executeToolLoop`  | Tool arguments were not valid JSON or not a JSON object (e.g. array/primitive).         |
| `MISSING_HANDLER`       | `executeToolLoop`  | Tool was advertised in `availableTools`, but no matching handler or `executor` exists.  |
| `TOOL_EXECUTION_FAILED` | `executeToolLoop`  | Handler threw an uncaught exception or `JSON.stringify()` threw (e.g. circular object). |
| `INVALID_TOOL_RESULT`   | `executeToolLoop`  | Handler returned `undefined` (no JSON representation).                                  |
| `CALL_LIMIT_EXCEEDED`   | `executeToolLoop`  | Global `tools.maxCalls` budget was exhausted mid-round; remaining calls were skipped.   |
| `TOOL_LIMIT_REACHED`    | `limitTool`        | Per-tool `ToolSpec.maxCalls` cap was reached.                                           |
| `VALIDATION_ERROR`      | Handler convention | Zod `safeParse()` rejected model arguments (model can self-correct).                    |

::note
**Prompt-like steering messages injected via `{ role: "tool" }`.** Every entry in the table above is sent directly to the model as the `content` of a `{ role: "tool", tool_call_id }` message in `{"error":{"code":"...","message":"..."}}` format. In particular, when a tool exceeds its per-tool `ToolSpec.maxCalls` cap, `limitTool()` injects the following instruction directly into the tool result:

```json [Exact tool-role message injected by limitTool()]
{
  "error": {
    "code": "TOOL_LIMIT_REACHED",
    "message": "<toolName> has been called <max> times already. Do not call it again — synthesize the final answer from the results you already have."
  }
}
```

None of the wrappers (`limitTool`, `withToolCache`, `trackTool`) inject `system` messages; any trailing synthesis `system` prompt comes from `executeToolLoop()` (see [Injected prompts and error messages](/tools/tool-loop#injected-prompts-and-error-messages)).
::

### Common failure modes

| Symptom                                                                    | Likely cause                                                                                           | Fix                                                                                                       |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Model gets `TOOL_EXECUTION_FAILED` with no useful detail                   | Handler threw an exception instead of returning `toolError()`, or returned a circular / `BigInt` value | Catch domain errors inside the handler and return `toolError(code, message)`.                             |
| Same tool call misses cache when optional defaults are omitted             | `withToolCache()` hashed raw args before Zod applied `.default(...)`                                   | Run `schema.safeParse(args)` inside `cache.normalizeArgs`.                                                |
| Broken/empty upstream response stays cached for hours                      | Handler returned a custom failure shape without `ok: false`, truthy `error`, or `toolError()`          | Return `toolError(...)` or `{ ok: false, error: "..." }` on failures.                                     |
| `tool_end.preview` is empty in browser SSE, yet model answered correctly   | `stream.emitResult` is `"none"` (default for `search_db`, `get_document`, `extractor`)                 | Intended for privacy/bandwidth — set `emitResult: "preview"` or `"full"` if the UI needs result previews. |
| One batch call spawns 20 concurrent HTTP requests despite `concurrency: 2` | `ToolSpec.concurrency` limits parallel _tool calls_, not array items inside one call                   | Cap per-item concurrency inside the handler itself.                                                       |
